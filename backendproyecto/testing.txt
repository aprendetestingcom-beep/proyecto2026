1. ALCANCE DE LAS PRUEBAS
------------------------------------------------------------------------------

Las pruebas cubren las 4 APIs CRUD generadas en Node.js, tabla por tabla:

  - administrador : /api/administrador
  - clientes      : /api/clientes
  - personal      : /api/personal
  - servicios     : /api/servicios

Para cada API se verifica el ciclo CRUD completo:

  C -> POST   /api/{recurso}          (crear, 201)
  R -> GET    /api/{recurso}          (listar, buscar y paginar, 200)
  R -> GET    /api/{recurso}/:id      (obtener uno, 200)
  U -> PUT    /api/{recurso}/:id      (reemplazo completo, 200)
  U -> PATCH  /api/{recurso}/:id      (actualización parcial, 200)
  D -> DELETE /api/{recurso}/:id      (borrar, 204)

Además se prueban:

  - Validaciones de campos obligatorios y formatos (HTTP 400).
  - Restricciones de unicidad de la base (HTTP 409).
  - Recursos inexistentes e identificadores inválidos (HTTP 404/400).
  - Valores por defecto definidos en la base o en el controlador.
  - Respuestas JSON uniformes: { data }, { data, meta } o { error }.
  - Que el hash de la clave del administrador nunca se exponga.
  - Que las claves se guarden hasheadas con scrypt y se puedan verificar.
  - Búsqueda por texto (?search=), paginación (?limit= y ?offset=) y filtro
    por hotel (?idHotel=) en personal.

No se prueban: login/autenticación (la API no tiene endpoints de sesión),
interfaz gráfica, rendimiento, concurrencia, seguridad ofensiva, ni fallas
de infraestructura. Ver sección 6.

2. ARCHIVOS DE PRUEBA
------------------------------------------------------------------------------

scripts/test-administrador.js  -> 10 pruebas de la tabla administrador.
scripts/test-clientes.js       -> 10 pruebas de la tabla clientes.
scripts/test-personal.js       -> 10 pruebas de la tabla personal.
scripts/test-servicios.js      ->  9 pruebas de la tabla servicios.
scripts/test-helpers.js        -> utilidades comunes: levanta la API en un
                                  puerto aleatorio, ejecuta peticiones HTTP,
                                  valida códigos de estado, genera códigos
                                  únicos y limpia los datos creados.

Cada archivo es autónomo: inicia el servidor Express dentro del mismo
proceso, usa la base configurada en .env y cierra todo al finalizar.

------------------------------------------------------------------------------
3. CÓMO EJECUTAR
------------------------------------------------------------------------------

Todas las pruebas:

    npm test

Una tabla en particular:

    npm run test:administrador
    npm run test:clientes
    npm run test:personal
    npm run test:servicios

Requisito: conexión disponible a la base configurada en .env. No hace falta
ejecutar "npm start" ni cargar datos manualmente. Al finalizar, cada script
elimina los registros que creó.

------------------------------------------------------------------------------
4. ESTRATEGIA Y DATOS DE PRUEBA
------------------------------------------------------------------------------

- Se usa la API real contra la base real (pruebas de integración).
- El servidor se levanta en un puerto libre (0) en 127.0.0.1.
- Cada ejecución genera un código único (fecha en base 36 + aleatorio) que se
  incluye en nombres, emails, usuarios y NIF. Así no se choca con los 10
  registros de seed ni con ejecuciones anteriores.
- Los registros se crean con IDs autoincrementales y se eliminan en un hook
  "after", en orden inverso (primero personal, luego el hotel de apoyo).
- Los tests de personal crean un hotel de apoyo mediante POST /api/clientes
  para usar un idHotel válido; ese hotel también se elimina al final.
- Los tests de administrador consultan la base directamente solo para
  comprobar que la clave almacenada es un hash scrypt verificable.
- Los tests se ejecutan de forma secuencial (--test-concurrency=1) para evitar
  interferencias entre tablas y facilitar la lectura del resultado.

5. CASOS DE PRUEBA

5.1 ADMINISTRADOR - scripts/test-administrador.js
------------------------------------------------------------------------------

ADM-01  POST /api/administrador
        Crea un administrador completo.
        Esperado: 201; devuelve idAdministrador entero, nombre, email en
        minúsculas, usuario y móvil; NO incluye el campo Clave.
        Verifica en la base que Clave sea un hash scrypt y que la contraseña
        original se pueda verificar con verifyPassword().

ADM-02  GET /api/administrador?search=CODIGO&limit=5&offset=0
        Esperado: 200; meta.limit=5, meta.offset=0, meta.total >= 1; el
        registro creado aparece en data; ningún registro expone Clave.

ADM-03  GET /api/administrador/:id
        Esperado: 200; devuelve el registro correcto y sin Clave.

ADM-04  PUT /api/administrador/:id
        Reemplaza nombre, email, móvil, usuario y contraseña.
        Esperado: 200; datos actualizados; la nueva clave queda hasheada y
        verificable, y la anterior deja de verificar.

ADM-05  PATCH /api/administrador/:id
        Actualiza solo N°Móvil y luego lo envía como null.
        Esperado: 200 en ambos casos; el email no cambia; el móvil queda
        actualizado y luego en null.

ADM-06  POST /api/administrador con email duplicado y con usuario duplicado.
        Esperado: 409 en ambos casos, con error.code = ER_DUP_ENTRY.

ADM-07  POST /api/administrador con body vacío, email inválido y clave corta.
        Esperado: 400; en el body vacío, details.missing indica los cuatro
        campos obligatorios.

ADM-08  GET /api/administrador/0 y /api/administrador/abc
        Esperado: 400 por identificador inválido.

ADM-09  POST /api/administrador sin N°Móvil.
        Esperado: 201; N°Móvil = null; sin Clave en la respuesta.

ADM-10  DELETE /api/administrador/:id
        Esperado: 204 al borrar; 404 al consultar después; 404 al repetir
        el borrado.

6. FUERA DEL ALCANCE
------------------------------------------------------------------------------

- Autenticación y autorización: la API no implementa login, tokens ni roles;
  solo se prueba el almacenamiento hasheado de la clave del administrador.
- Interfaz de usuario / frontend: no existe en este repositorio.
- Pruebas de carga, estrés, concurrencia o tiempos de respuesta.
- Pruebas de seguridad ofensiva (fuerza bruta, XSS, CSRF, rate limiting).
  Sí se verifica de forma indirecta el uso de consultas parametrizadas.
- Integridad referencial real: los .sql definen claves foráneas lógicas, sin
  FOREIGN KEY; no se prueba el rechazo de un idHotel inexistente.
- Disponibilidad, respaldo y recuperación de la base de datos.
- Compatibilidad con otros motores o versiones distintas de MySQL/MariaDB.
- Envío real de correos, archivos o servicios externos.
- Cobertura de líneas/código (no se usa herramienta de cobertura).

------------------------------------------------------------------------------
7. LIMPIEZA Y DATOS
------------------------------------------------------------------------------

- Cada script registra los IDs que crea y los elimina en el hook "after".
- El orden de limpieza es inverso: personal -> hotel de apoyo -> clientes ->
  servicios -> administrador según corresponda.
- Un DELETE repetido devuelve 404 y se ignora durante la limpieza.
- Los 10 registros de seed de cada tabla no se modifican ni se eliminan.
- Tras ejecutar npm test, el conteo de las tablas debe seguir siendo 10 por
  tabla (verificable con npm run db:test).
